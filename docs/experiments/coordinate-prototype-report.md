# D-014 坐标确定性原型报告

## 结论

日期：2026-08-22。

**事实：** D-014 的整数规范化坐标、ties away from zero 舍入、clamp、CSS 缩放、Canvas backing store、DPR 上限和任意抓取点规则已通过两个独立参考实现及本地浏览器验证。阶段 0 的坐标确定性门禁通过。

**不代表：** 本报告不证明通过者是真人，不验证轨迹启发式攻击识别能力，也不产生真实用户误拒率。当前容差仍是 v0.1 初始工作参数，经验性校准属于 v0.1 发布前门禁。

## 原型范围

原型位于 `experiments/coordinate-prototype/`，只包含静态 HTML、CSS、原生 ES module、Node runner 和 PowerShell runner：

- 无 npm/Maven 项目或第三方运行时依赖。
- 背景和拼图片完全由 Canvas 程序绘制。
- 未使用外部图片、字体、轨迹样本或数据集。
- 客户端结果明确标记为不可信，不作为业务授权证据。

## 发现与解释

1. 非整数 CSS 布局会被浏览器量化为实际布局值，例如请求 333.3 px 得到 333.296875 px。规范使用一次 `getBoundingClientRect()` 快照是必要的，不能用配置字符串代替真实内容矩形。
2. 实际鼠标坐标以整数视口像素注入时，在非整数布局中产生了 192 N 的终点误差，约等于 0.064 CSS px。它远小于当前 12500 N 工作容差，也说明 ±1 N 结构一致性只适用于同一公式重算，不能拿它当用户答案容差。
3. DPR 只影响 backing store；同一目标位移在所有组合中保持相同 Normalized 结果。
4. 任意抓取点不改变最终拼图片位置，验证了不能假设用户从中心抓取。

## 未覆盖与后续门禁

- `pointercancel`、失去 capture、页面隐藏和拖动中 resize 已在原型实现取消路径，但本轮浏览器控制接口无法在按键保持期间插入第二个动作；这些路径需在 v0.1 Playwright 自动化中用可控事件时序验证。
- 未覆盖浏览器旋转、透视、斜切、非等比拉伸；它们本来就不属于 v0.1 保证范围。
- 未采集真实用户轨迹。最终容差、触控误拒率和攻击通过率必须在 v0.1 发布前单独评估，并更新 `policyVersion`。
- **报告编写时的后续要求（现已完成）：** 当时 Java Core 尚未建立；现在冻结坐标向量已经成为 Java 17/21 构建的强制测试。若未来 Java 结果不一致，仍应先修实现，不能修改已冻结向量迁就实现。

## 阶段判断

**推论：** 已有证据足以证明阶段 0 所需的坐标协议确定性；继续要求真实用户误拒率会依赖尚未允许建立的 Widget/Core，形成阶段循环。因此经验性容差校准应保持为 v0.1 发布门禁，而不是阶段 0 阻塞项。
