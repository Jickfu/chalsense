# ChalSense v0.1 威胁模型

## 文档状态与范围

- 状态：阶段 0 安全基线；关键消费、故障、坐标、存储、站点模型、调用方/Origin、TTL 与 Redis Store 语义已由 D-013～D-018、D-021～D-030 批准，最终容差数值仍待经验性验证。
- 适用范围：D-007 已批准的滑块拼图、Java Core、Redis 状态实现、Web Component、Spring Boot Starter 与薄 HTTP 服务层。
- 不在范围：D-012 延后的 PoW、设备指纹、云级风险平台、文字点选、业务账户认证本身。
- 更新触发：协议、安全边界、状态存储、资源交付、默认遥测或安全主张变化时必须同步评审本文。

本文使用以下标签区分结论性质：

- **事实**：可由当前系统性质、标准或已观察行为直接支持。
- **已批准决策**：来自 `docs/decisions/README.md` 的 D-001～D-030。
- **推论**：由事实和攻击模型推导，但仍需实现与测试验证。
- **建议**：本轮设计给出的方案，批准前不构成稳定承诺。
- **工作假设**：为了完成威胁分析暂时采用，后续可能调整。

## 安全目标

1. 使挑战、验证结果和票据不能被低成本猜测、重复使用或跨场景挪用。
2. 保证同一挑战最多只有一个验证尝试取得其状态，同一票据最多成功消费一次。
3. 将 `siteKey`、`action`、`contextDigest` 与验证结果绑定，并在消费时统一检查。
4. 对客户端输入实施完整解析、边界和资源限制；客户端成功回调不作为业务授权证据。
5. Redis 或密钥基础设施异常时不静默绕过验证；高风险动作默认失败关闭。
6. 默认只处理完成验证所必需的数据，不采集设备指纹，不把完整轨迹或票据写入普通日志。
7. 给接入方提供可组合的纵深防御信号，同时准确说明其能力上限。

## 明确不保证的能力

**已批准决策与产品边界：** ChalSense 不保证通过者一定是真人，也不能单独阻止计算机视觉、自动化浏览器、人工打码、设备农场、撞库、薅羊毛或账户接管。它不替代限流、MFA、密码安全、账户风险策略和人工处置。

**事实：** 客户端代码、挑战图片和协议均可被攻击者观察；安全性不得依赖隐藏 JavaScript、隐藏算法或图片 URL 难猜。

**推论：** v0.1 的位置匹配和轨迹启发式主要提高低成本批量自动化的成本，不构成身份、意图或“人类性”的密码学证明。

| 服务容量与业务可用性 | 可用性、可恢复性 | 资源生成、Redis 或验证接口被打满，阻断合法用户 |

## 参与方与信任级别

| 参与方 | 信任级别 | 说明 |
| --- | --- | --- |
| 最终用户 | 不可信 | 可能是合法用户，也可能主动操纵请求和客户端代码 |
| 浏览器、WebView、Web Component | 不可信执行环境 | 可被调试、替换、自动化；坐标、轨迹、时间戳和成功事件均不可作为可信事实 |
| 业务前端 | 不可信网络调用方 | 只能携带挑战和票据，不得持有服务端密钥或消费权限 |
| 业务后端 | 受信任调用方，但可能配置错误或被攻陷 | 创建业务绑定、调用票据消费，并负责最终业务决策 |
| ChalSense Core | 核心信任域 | 唯一实现挑战与票据状态机、绑定校验和验证语义的组件 |
| 薄 HTTP 服务层 / Starter | 受信任适配层 | 负责认证、传输、配置和 Core 装配，不得复制状态机 |
| Redis / 兼容状态服务 | 高敏感基础设施 | 持有短期状态；必须限制网络、账号和命令权限 |
| 资源存储或 CDN | 半受信任 | 可以提供挑战资源，但不应获得答案、票据或业务明文上下文 |
| 运维与发布人员 | 特权主体 | 可接触密钥、配置、构件和生产指标，需要最小权限与审计 |
| 业务限流、MFA、风险系统 | 独立控制层 | 与 ChalSense 组合决策，不能假设 ChalSense 通过即请求可信 |

## 信任边界与数据流

```text
不可信浏览器
  │  challenge / resources / verify / verificationTicket
  ▼
公开 HTTP 边界：TLS、Origin/CORS、请求限制、公开限流
  │
  ▼
适配层边界：站点解析、受信任服务认证、结构化错误
  │
  ▼
ChalSense Core：唯一安全状态机与绑定校验
  │                         │
  ▼                         ▼
状态存储边界：Redis       资源边界：生成器/对象存储/CDN
  │
  ▼
受信任消费边界：业务后端 → Core Java API 或受信任 HTTP API
  │
  ▼
业务授权边界：验证码结果 + 限流 + MFA + 账户与场景风险
```

关键边界规则：

- 公开 `verify` 与受信任 `verificationTicket.consume` 必须是不同授权面；浏览器不能直接消费票据。
- 业务不得直接读写 ChalSense Redis Key；D-011 要求所有消费进入 Core 的统一语义。
- 资源 URL 和图片不是秘密。资源服务不得根据“URL 没人知道”授予额外信任。
- `contextDigest` 是业务提供的不透明绑定值；ChalSense 不接收账号、密码或业务表单明文。

## 攻击者能力

假设攻击者可以：

- 查看、修改和重放全部浏览器请求，替换 Web Component，伪造 Pointer Events、坐标、轨迹、相对时间和成功回调。
- 并发调用 `challenge`、`verify` 和受保护业务接口，控制请求顺序、延迟、断连与重试。
- 获取自己会话中的挑战图片、协议字段和失败结果，并使用 OCR、OpenCV、浏览器自动化或人工打码。
- 猜测 `siteKey`、枚举公开动作、从日志、浏览器扩展、XSS、Referer 或代理中尝试窃取票据。
- 利用畸形 JSON、超大轨迹、极端数值、重复字段、Unicode 差异和反序列化边界攻击实现分歧。
- 对公开接口制造资源耗尽，诱发 Redis 超时、主从切换、网络分区或结果不确定。
- 在业务后端密钥泄露后调用受信任接口；此时 ChalSense 只能通过密钥轮换、最小权限和审计缩小影响。

默认不假设攻击者能够突破现代密码原语、TLS、正确配置的操作系统隔离或安全随机数生成器。若这些前提失效，系统不能维持对应安全属性。

## 滥用场景、控制与残余风险

| ID | 滥用场景 | 主要控制 | 残余风险 |
| --- | --- | --- | --- |
| T-01 | 猜测或枚举 `challengeId` / ticket | `challengeId` 固定 128 位、ticket 固定 256 位且存储查找 key 只使用 `SHA-256(rawTicketBytes)`；统一模糊的不可用错误；限流 | 端点和 `siteKey` 仍可枚举；令牌可从其他漏洞泄露 |
| T-02 | 对同一挑战反复试探答案 | 一旦请求已通过身份、大小和基本路由检查并识别出挑战标识，就原子取走状态；成功与失败均不恢复 | 攻击者可批量创建新挑战；需站点、IP/网络和业务维度限流 |
| T-03 | 并发验证同一挑战 | 原子 `take`；只有一个调用取得状态，其余统一为不可用 | 网络故障时客户端无法确认是否已消费，只能创建新挑战 |
| T-04 | 重放或并发消费票据 | ticket 只存摘要；原子取走后再做全部绑定检查；任一消费尝试均不恢复 | 窃取者可能先于合法请求消费，造成拒绝服务但不能重复成功 |
| T-05 | 跨站点、跨动作或跨上下文挪用 | 创建时固化 `siteKey`、`action`、`contextDigest`；低熵业务值使用业务密钥 HMAC；消费时常量时间比较并要求全部一致 | 业务生成错误、复用错误用途密钥或直接散列低熵值会削弱绑定并产生可关联标识；业务后端被攻陷后无法防护 |
| T-06 | 伪造客户端成功回调 | 回调只携带 ticket；业务后端必须调用 Core 消费后才决策 | XSS 可窃取未消费 ticket；仍需 CSP、输出编码和前端供应链防护 |
| T-07 | 篡改坐标、时间戳或轨迹 | 所有字段不可信；严格整数范围、点数、顺序、持续时间和状态检查；答案只在服务端 | 高质量合成轨迹与真实轨迹可能不可区分；不得宣传为 AI 风控 |
| T-08 | 图片分析、题库预计算或资源抓取 | 足量合法资源、随机几何、挑战短期有效、限速与攻击回归 | 计算机视觉和人工服务仍可通过；图片混淆只能增加成本 |
| T-09 | 请求体、图片生成或轨迹导致资源耗尽 | 请求体/数组/数值上限；生成并发与超时；分层限流；容量指标；背压 | 攻击可使合法用户失败；失败关闭会放大可用性影响 |
| T-10 | 利用解析器差异绕过 | 明确 JSON 子集、拒绝重复字段与非整数数值、稳定 Schema、跨语言测试向量 | 不同网关可能先行规范化请求；部署文档需约束代理行为 |
| T-11 | Redis 故障或主从切换产生双消费 | 单 key 原子操作；强制从可写主节点执行；超时/未知结果失败关闭且不重试同一凭据；D-030 延期可能自动重放命令的 Cluster 入口 | 异步复制故障切换仍可能丢失最近写入；严格一次性需要部署持久性与故障模型配合 |
| T-12 | Redis Key 碰撞或跨租户读取 | 固定命名空间、环境隔离、ticket/ID 摘要作为 key、ACL 最小权限、随机 salt/secret | 共用 Redis 的管理员仍能读取或删除数据；应视 Redis 为高敏感系统 |
| T-13 | 已取走状态损坏、版本未知或迁移错误 | 严格 reader；`Unreadable` 与 `Failed`/`Unknown` 分离；不恢复损坏字节；Core 失败关闭并记录低基数事件 | 单次凭据不可恢复；需依靠部署监控、兼容 reader 和发布回滚降低可用性影响 |
| T-13 | 密钥泄露或错误轮换 | `keyId`、独立用途密钥、重叠验证窗口、审计、紧急吊销、不把密钥交给浏览器 | 在发现和吊销前可伪造受信任调用；现有已签发/已存状态需明确吊销策略 |
| T-14 | Origin/CORS 配置错误 | `siteKey` 绑定允许 Origin；精确 scheme/host/port；拒绝通配符凭据；服务端调用单独认证 | Origin 不是身份认证，非浏览器客户端可伪造；主要用于浏览器滥用与配置隔离 |
| T-15 | 日志或指标泄露 | 禁止记录答案、完整轨迹、ticket、资源签名 URL 和明文上下文；标识只记录截断摘要 | 调试开关和外部 APM 仍可能捕获请求体；需发布前检查默认配置 |
| T-16 | 无障碍用户被排除或被迫披露更多信息 | 明确替代路径；可键盘操作与焦点管理；不以指纹换取“无感” | v0.1 视觉挑战仍不可供所有用户完成；替代流程由接入方提供且需纳入评审 |
| T-17 | 恶意或无许可素材/依赖 | 来源与许可证清单、构件校验、依赖审查、DCO、SBOM 路线 | 上游被攻陷或许可证元数据错误仍需人工审查和响应 |
| T-18 | 时钟回拨/漂移绕过过期 | 状态存储 TTL 是硬上限；Core 同时比较服务端时间；测试注入时钟；监控漂移 | 跨节点大幅漂移会造成提前失效或短暂延长；不接受客户端绝对时间 |

## 基础设施故障安全语义

1. 创建挑战时，状态未确认持久化则不得向客户端返回可用挑战。
   只有存储明确返回 ID 已存在时，Core 才能换用新的随机 ID 重试；明确失败或结果未知均不重试，且不返回 `challengeId`。
2. 验证或消费的原子 `take` 超时后，结果为 **未知**；服务端必须失败关闭，调用方不得以同一挑战或 ticket 自动重试。
3. 原子取走成功后，后续校验、签发或响应失败都不得恢复挑战或 ticket。恢复会重新开放试探或双消费窗口。
4. 验证成功但 ticket 状态未确认写入时不得返回 ticket；客户端只能创建新挑战。
5. Redis 从节点、只读副本或最终一致缓存不能承载安全状态机写入。
6. 健康检查必须区分进程存活和安全依赖就绪；依赖不就绪时公开端点返回可重试的服务不可用，而不是绕过。

**残余风险：** 若部署采用异步复制并在已确认写入尚未复制时故障转移，最近状态可能丢失。是否要求 Redis 持久化、复制确认或特定托管 SLA 属于部署安全等级，而非 Core 单靠 API 可以消除的问题。

## 隐私与数据生命周期

| 数据 | 默认保存位置 | 最长生命周期建议 | 日志规则 |
| --- | --- | --- | --- |
| Challenge State / answer | Redis | 挑战 TTL 加极短清理余量 | 禁止记录答案和原始状态 |
| 有限轨迹 | 仅验证请求内存；如需状态则随挑战短期存在 | 请求结束即释放；默认不持久化 | 禁止写入普通日志 |
| Ticket State | Redis | ticket TTL | 禁止记录原始 ticket |
| `contextDigest` | Challenge/Ticket State | 对应 TTL | 只允许截断的二次摘要用于关联诊断 |
| IP / Origin / 原因码指标 | 接入方和服务观测系统 | 由部署方隐私政策明确 | 不与完整轨迹组合形成行为画像 |
| 设备指纹 | 不采集 | 不适用 | D-005 禁止默认采集 |

## 必须验证的安全性质

- 属性测试：同一 challenge 并发 N 次，取得状态的调用数严格为 1；同一 ticket 成功消费数严格为 1。
- 故障注入：原子操作前失败、执行结果未知、取走后失败、ticket 写入失败、响应断连。
- 解析差异：重复 JSON key、指数数字、小数、负数、越界整数、额外字段、错误 Base64url、Unicode 与超大数组。
- 绑定矩阵：逐一改变 `siteKey`、`action`、`contextDigest`、`protocolVersion`，消费均失败且 ticket 已不可再次使用。
- 时钟边界：恰好到期、到期前 1 ms、到期后、时钟回拨和 Redis TTL 先到期。
- 隐私检查：默认日志、异常栈、指标标签和 tracing 不含答案、完整轨迹、原始 ticket 或业务明文。
- 攻击回归：随机位置、固定/线性/贝塞尔/重放轨迹、OpenCV 缺口识别与批量新建挑战。

## 阶段 0 评审门槛

威胁模型可以进入批准状态前，必须：

1. 与协议状态机、错误语义、坐标规范和测试向量互相引用且无冲突。
2. 原子消费发生点、基础设施“结果未知”语义、ticket 形态和绑定字段必须保持与 D-013、D-018 一致。
3. 明确首版部署文档对 Redis 复制/持久性、TLS、ACL 和密钥管理的最低要求。
4. 为视觉挑战之外的替代流程保留接入要求，不把无障碍责任描述成可选优化。
